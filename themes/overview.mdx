The Formbox Renderer is fully headless: every DOM element, layout decision, and style belongs to the theme. The renderer owns form logic — state, validation, conditional visibility, calculated expressions — and calls into your theme components to produce the actual UI. Swapping the theme changes everything the user sees without touching a line of form logic.

## How the theme contract works

A `Theme` is a plain TypeScript object mapping slot names to React components. The renderer imports that object, calls each component with strongly typed props, and never touches the DOM or sets a `className` or `style` attribute itself. If you want a different button, input, or label, you replace the component in the theme object.

All inputs are **controlled**: callbacks receive parsed values, not DOM events. A `TextInput` receives an `onChange: (value: string) => void` callback. A `NumberInput` receives `onChange: (value?: number) => void`. The renderer manages state; the theme manages presentation.

Theme components never receive `className` or `style` props from the renderer. Styling is entirely the theme's responsibility — use CSS modules, Linaria, Tailwind, a design system, or inline styles as you prefer.

Four production-ready themes ship with Formbox Renderer. Each is a separate npm package with its own stylesheet.

Each theme package exports a `theme` object typed as `Theme` and a CSS file you must import manually:

```tsx
import { theme } from "@formbox/hs-theme";
import "@formbox/hs-theme/style.css";
```

<Note>
Theme CSS is **not** injected automatically. Always import the stylesheet alongside the theme object, or the layout and tokens will be missing.
</Note>

## The Theme type

`Theme` is exported from `@formbox/theme`. It is a record of 37 required component slots plus an optional `customExtensions` field. Every slot must be present — the type is strict and the TypeScript compiler will report missing slots.

```ts
import type { Theme } from "@formbox/theme";
```

The slots cover every UI primitive the renderer needs:

## Renderer composition overview

The renderer wraps your theme components in a predictable tree. You control layout within each component; the nesting shows where labels, errors, and actions appear relative to each other.

**Typical question node:**

```text
QuestionScaffold
  Label
  AnswerList (or a single control)
    AnswerScaffold (per answer)
      control (TextInput / Select / etc.)
      remove action (when onRemove is provided)
      children (nested nodes)
      errors (Errors)
  Errors (question-level)
```

**Repeating group list:**

```text
GroupList
  Label (only when the list has text)
  GroupScaffold (per instance)
    remove action (when onRemove is provided)
    errors
  add action (when onAdd is provided)
```

**Non-repeating group:**

```text
GroupScaffold
  Label (when visible)
  Stack (child nodes)
  Errors
```

## Renderer guarantees

- `id`, `ariaLabelledBy`, and `ariaDescribedBy` values are unique within a render and stable for a given node or answer.
- `ariaDescribedBy` strings are already space-joined; forward them as-is.
- Option tokens are stable across renders; tokens remain safe as React keys.
- `label` and `children` props are ready-to-render `ReactNode` values — no further processing needed.
- When a stored answer uses a legacy or custom option value, the renderer passes a disabled entry so the selection still renders correctly.
